# Архитектура и демонстрация

## Слои приложения

| Слой | Ответственность |
| --- | --- |
| Routes / middlewares | Маршрутизация, аутентификация, роли, валидация, лимиты |
| Controllers | Чтение HTTP-запроса, вызов сервиса, формирование ответа |
| Services | Прикладные операции и проверки |
| Repositories | Запросы к PostgreSQL, транзакции и блокировки |
| Models / migrations | Структура данных и ограничения БД |

Zod проверяет входные данные

Общий обработчик ошибок возвращает `error.code`, `message`, `requestId` и при необходимости `details`

## Данные

- `request_assignees`: специалист, роль `lead/member`, часы
- `users.role`: `viewer`, `technician`, `admin`
- `users.technician_id`: необязательная связь со специалистом
- Оборудование и заявки используют soft delete
- Удаление связанных площадок и специалистов ограничено внешними ключами

## Транзакции

| Операция | Граница атомарности |
| --- | --- |
| Создание заявки | Проверка оборудования с блокировкой, заявка и начальная история |
| Смена статуса | Блокировка заявки, проверка назначения и перехода, обновление статуса и история |
| Замена бригады | Блокировка заявки, удаление старого состава и запись нового |
| Снятие исполнителя | Блокировка заявки, проверка ограничений и удаление назначения |

Импорт обрабатывает элементы отдельно: ошибка одной заявки не отменяет уже созданные

## Аутентификация

- Пароли хешируются bcrypt
- Access token - JWT с ограниченным сроком действия
- Refresh token хранится у клиента в HttpOnly cookie, в БД - его хеш
- Защищённый запрос проверяет пользователя и активную сессию в БД
- Logout отзывает сессию, её access token перестаёт приниматься

Назначение бригады связывает заявку со специалистом, а не меняет роль аккаунта

## Развёртывание и мониторинг

Схема стека приведена в [README](../README.md).

- Nginx проксирует API, документацию и Web UI
- API доверяет одному прокси, Nginx задаёт клиентский IP
- `init` выполняет подготовку БД до запуска API
- Prometheus собирает HTTP-метрики API
- Grafana объединяет метрики Prometheus и SQL-отчёты PostgreSQL
- `/metrics` закрыт снаружи, Grafana защищена Basic Auth

## Ограничения

- Один экземпляр API, rate limit хранится в памяти процесса
- Автор последующей смены статуса - ID пользователя, начальная запись использует `api-client`
- Alert отображается в Grafana

## Сценарий защиты

Использовать одно окружение для API и Grafana

### Подготовка

1. Открыть приложение, Swagger и прикладной дашборд Grafana
2. Войти в приложение как администратор
3. В Swagger выполнить `POST /api/auth/login`
4. Скопировать `data.accessToken` в Authorize - bearerAuth, без префикса Bearer
5. Через `GET /api/equipment` выбрать оборудование
6. Через `GET /api/technicians` выбрать двух специалистов

### Заявка и бригада

Создать заявку через `POST /api/requests`:

```json
{
  "equipmentId": "<ID оборудования>",
  "title": "Демонстрация обслуживания",
  "description": "Проверка сквозного сценария",
  "priority": "high"
}
```

Сохранить ID заявки. Ожидается `201`, статус `new`

Назначить бригаду через `POST /api/requests/{id}/assignees`:

```json
{
  "assignees": [
    {
      "technicianId": "<ID первого специалиста>",
      "role": "lead",
      "hours": 4
    },
    {
      "technicianId": "<ID второго специалиста>",
      "role": "member",
      "hours": 2
    }
  ]
}
```

Ожидается `204`. Проверить состав через `GET /api/requests/{id}`.

### Статусы и история

Последовательно выполнить `PATCH /api/requests/{id}/status`:

```json
{ "status": "in_progress" }
```

```json
{ "status": "done" }
```

Оба ответа - `200`

В `GET /api/requests/{id}/history` показать переходы и автора изменений

### Grafana

Обновлять прикладной дашборд после каждого этапа:

- создание: число заявок `new` и приоритета `high` увеличивается
- назначение: плановые часы выбранного оборудования увеличиваются на 6
- начало работ: заявка переходит из `new` в `in_progress`
- завершение: увеличивается число `done`, пересчитывается среднее время закрытия
